# 备份、恢复与数据保留方案

## 范围与实现边界

按 deploy/scripts/backup-local.sh、verify-backup-restore.sh、systemd 配置核对。当前实现单机加密副本、通过SSH拉取并复核的异机加密副本、一次性解密材料转存入口和隔离恢复验证；不集成外部对象存储/密钥库，不提供自动生产切换。离线注销审计工具已实现，完整生产恢复仍需业务/文件一致性和目标机 RTO 验收。具体频率/保留/目标及已执行结果在案例确认，服务器基线每日一次、7日/4周，异机副本不自动删除。

数据库管理员在 db 容器内经本地 socket 执行 pg_dump -Fc → 验证目录 → 从 app 容器复制 exports → manifest记录时间及镜像 → tar流经OpenSSL CMS AES256/RSA加密 → 全量解密列目录核验 → 原子放入daily并算SHA256 → 每周最新副本硬链接 → 轮转 → last-success。flock防并发重复执行，失败写系统日志并清理本次明文临时目录。

## 一次性准备

新环境由 `npm run environment -- bootstrap <目标>` 创建0700备份目录、RSA3072备份加密材料、systemd单元并完成首次备份，不再要求运维复制一串OpenSSL和systemctl命令。脚本先检查目标文件不存在并以0600落盘；密钥不可重复生成覆盖，否则旧副本无法解密。已有环境修复时回查 `deploy/scripts/bootstrap-environment.sh` 的同一状态步骤，不手工另造第二套约定。

这套证书用于备份加密，独立于 HTTPS CA，不能发给客户端当根信任。生成后立即按[统一运维入口](operations.md)检查指纹、复制异机归档并完成解密材料托管。

脚本固定容器名 my-bill-db-1/my-bill-app-1/my-bill-proxy-1、库my_bill和目录；改项目名、库名或路径须同步脚本和验证，不能只改 env。宿主需要 `python` 命令与 date 的ISO周格式能力，备份目录、解密密钥和Docker访问仅root。

## 执行、校验与调度

日常执行使用稳定入口：

```bash
npm run ops -- backup <目标>
npm run ops -- backup-list <目标>
npm run ops -- backup-verify <目标> YYYY-MM-DD
npm run ops -- recovery-drill <目标> YYYY-MM-DD
```

`backup` 同时核对本次成功时间并拉取异机加密副本；首次初始化已经安装并启用timer。底层 `backup-local.sh`、systemd和 `verify-backup-restore.sh` 命令只用于脚本实现或故障诊断，正常运维不逐条重放。

先核对宿主时区 Asia/Shanghai；OnCalendar 用宿主本地时间，脚本里的 TZ 只影响归档日期，不能替代 timer 时区。其他业务依赖宿主时区时，不擅自全局修改，应为定时配置设计独立时区方案并验证。

保留最近7个日历日和最近4个ISO周内的成功副本，各最多7/4个；不是“永远至少7份”。断电后 Persistent=true 补触发；失败仅有日志，通过本机 journald/systemd 告警，外部消息渠道未配置。last-success 是最后成功记录，失败不会改成失败标记，必须同时检查新鲜度和服务结果；管理概况通过独立只读状态目录接入最近尝试结果与成功时间；应用不访问备份归档或密钥。

## 隔离恢复验证能证明什么

verify-backup-restore.sh 校验路径和checksum，在 --network none、无宿主端口、2GiB tmpfs、768MiB内存的临时PG中创建无登录引用角色，解密导入数据库后重新导出；结束只清理自身临时容器。其trust认证仅用于无网络临时实例，不得复用于生产。

该验证证明数据库归档可解析、对象和数据可读；不恢复导出文件、不保留生产所有者/权限（--no-owner/--no-privileges）、不验证应用登录/租户样本、不重放注销。数据超过tmpfs或资源限制时需另行规划隔离演练资源，不能调低校验掩盖失败。

## 真实业务恢复操作方案

1. 确认事故范围、恢复点、允许数据损失和维护窗口，阻断新写入；保全现库和导出卷用于追查，不能先覆盖唯一副本。
2. **覆盖数据库前**，独立保全尚未过期的 account_deletion_audit。若现库损坏导致无法取得，必须从独立可靠来源恢复注销事实；使用下述离线工具；若没有可靠的最新审计来源，仍存在已注销用户数据复活风险，禁止开放恢复库。
3. 验证副本checksum、加密密钥和隔离恢复；准备匹配PG版本的替代库/卷。通过正确角色与Flyway构建授权，不把隔离脚本的无权限导入直接作为生产恢复。
4. 恢复数据库及同一副本导出文件，按应用版本升级schema；恢复导出目录属主10001。备份先dump后复制文件，无跨资源一致快照，需逐条核验导出记录与文件状态，缺失/过期文件收敛为不可下载并按业务流程重建。
5. 导入保全的匿名注销审计，以不可逆主体指纹匹配恢复的账号，重放删除在线数据、会话及文件，保留必要审计。使用下述维护工具；本地隔离演练已有证据，目标恢复库必须单独验证。
6. 用至少两租户业务样本核验条数、金额、报表口径、下载、回收站、注销、权限和任务幂等，检查任务启动恢复；记录实际恢复时间，满足RTO后再放入口。
7. 新建备份、验证告警、记录案例的新恢复点与证据，保留事故原始副本到确认可清理。

以上定义恢复要求与实施顺序，不提供一键生产恢复承诺。每个实例须验证自己的恢复数据、业务和入口切换，并记录耗时；隔离演练与真实事故恢复须分别标注。已有样本规模、切换证据和未覆盖范围见[内网案例](cases/intranet-single-host.md)及[验收报告](../test-report.md)，不在通用方案中维护阶段状态。

## 风险与后续模式

| 类型 | 已确认限制 | 对策 |
|---|---|---|
| 整机丢失 | 同机副本和解密密钥可能同时丢失 | 只有另行确认并实现异机副本/密钥托管后，才可承诺灾备 |
| 在线备份 | 数据库与导出非一致快照 | 恢复验证文件状态，重要维护采用受控写入/任务暂停方案 |
| 保留策略 | 7日/4周无法代替180天注销审计恢复策略 | 覆盖前独立保全未过期注销事实，恢复后重放 |
| 可观测性 | 本机日志、巡检单元和管理概况；无外部通知 | 每 15 分钟检查服务、磁盘、证书及备份新鲜度；告警需运维查看 |

日常触发、列表、异机复制、checksum复核、解密材料转存和隔离恢复演练统一使用[运维入口](operations.md)。异机归档与私钥必须分别保管；只拉取加密文件或把两者放在同一台普通工作站，都不能宣称已满足整机灾备。

替代主机恢复时，`backup-key-restore` 只在目标密钥不存在时恢复托管材料，`offsite-recovery-drill` 将异机归档上传到隔离暂存区并验证解密/数据库重建；两者都不覆盖线上库。生产开放前仍须按“真实业务恢复操作方案”完成最新注销审计、导出文件、schema、业务样本和入口切换。

## 状态与本机告警部署

以 root 创建 `/var/lib/my-bill/operations`（0755，root 所有），由备份脚本原子发布 0644 的 `backup.properties`。应用仅只读挂载这个目录。首次接入先成功运行一次备份，再重建 app 容器。管理页成功只代表归档校验，不能替代完整恢复演练。

首次初始化入口安装并启用 `my-bill-monitor.service/.timer`；日常使用 `npm run ops -- status <目标>` 查看timer，使用 `npm run ops -- logs <目标>` 查看检查与告警，不再逐条复制systemctl/journalctl命令。非零退出令巡检单元标为失败，后续成功检查恢复。每15分钟检查容器、备份文件系统85%水位、叶证书30天到期阈值和备份26小时新鲜度。该巡检不读取个人账目，也不自动重启服务或删除数据。

## 注销审计离线维护工具

`run-app --recovery-tool` 为一次性 Java 维护模式，绑定回环随机端口并在完成后退出，禁用后台轮询、任务启动恢复和文件启动恢复，不增加 HTTP 接口。SQL 位于 `RecoveryAuditMapper.xml`，删除重放复用原注销应用服务与文件提交补偿。

1. 进入维护窗口并停止 app，阻断所有用户、管理员和后台写入，再从尚可读取的当前库执行 `MY_BILL_RECOVERY_ACTION=preserve`。用相同 app 镜像、数据库网络和 app secret，设置 `MY_BILL_RECOVERY_AUDIT_FILE` 为 UID10001 可写受控目录内的**新文件**，以 `/usr/local/bin/run-app --recovery-tool` 启动。不要向工具授予迁移或管理员数据库凭据。保全按 100 条游标分页导出未过期成功审计，只保存匿名指纹及审计字段；首尾标记用于拒绝截断文件，不提供密码学防篡改。立即把文件放入受控加密归档并保存校验值。
2. 将备份恢复到以 `my_bill_restore_` 开头的专用恢复库与独立导出卷。保持标准数据库角色、迁移授权、RLS 和原导出根路径；不要直接把 `--no-privileges` 的临时恢复结果视为生产就绪。
3. 使用该库实时 `current_database|inet_server_addr|inet_server_port|pg_postmaster_start_time` 指纹，设置 `MY_BILL_RECOVERY_EXPECTED_DB_FINGERPRINT`、`MY_BILL_RECOVERY_ACTION=replay` 和只读审计文件路径。工具先校验专用库名、指纹、格式、64MiB上限和结束计数，再导入未过期审计，按指纹匹配普通用户并重放租户数据与导出文件清理。已有审计不覆盖、重复执行不重复删除，也不延长原保留期。每次重放先收敛上次中断的文件隔离状态，避免账号已删但隔离文件残留。
4. 验证未注销租户及管理员不受影响、已注销账号与导出不可恢复、金额/报表口径和完整文件恢复通过后，才考虑受控切换。工具不能绕过生产库名门禁直接对线上库执行重放。

保全要求维护窗口内没有并发注销；如果当前库已损坏且没有独立可靠审计副本，应停止恢复开放流程，不能从旧备份推断之后无人注销。当前工具不承诺覆盖此类整机/数据源损失。审计文件不得由普通用户提供；文件校验和、私密传输与加密存储由维护流程保证。工具完成不等于业务 RTO 已达标，实测记录归部署案例。

### 命令与本地隔离验证

开发机执行 `bash scripts/test-recovery.sh`。脚本先编译测试后端，再创建一次性 PostgreSQL 集群，运行真实 HTTP/业务样本，保全审计、全库导出、恢复至 `my_bill_restore_drill` 并核对非空账目条数及十进制金额。恢复副本加入旧快照中已注销账号与导出文件的合成情景，再执行 CLI 重放两次，断言只减少该账号、文件消失、其余账目条数与金额不变。退出销毁集群，不读取生产连接。它不能替代目标机全量业务恢复或 RTO 证明。

离线容器的完整参数已封装在 `deploy/scripts/verify-recovery-tool.sh`，不再要求运维复制易误用的长 `docker run`。实现必须保持：专用internal网络、无宿主端口、只读根、受限tmpfs/内存/CPU/PID、capabilities全移除、`no-new-privileges`；数据库URL只能指向 `my_bill_restore_` 专用库，挂载独立恢复导出卷、应用密码、pepper和只读审计文件，不挂Docker socket、线上导出卷、管理员或迁移凭据。生产事故需要自定义参数时，应扩展并审查脚本，而不是在终端临时删减保护项。

`preserve` 使用 `MY_BILL_RECOVERY_ACTION=preserve`、当前库的应用 URL 和 secret、可写保全目录，省略预期指纹；必须先停止写入端，且输出文件不得已存在。`replay` 的实时指纹查询与 `RecoveryAuditMapper.xml` 的 `fingerprint` 保持完全一致，用应用角色、同一连接地址从恢复库取得；数据库重启后须重新核对。容器不发布端口、不挂 Docker socket、不挂线上导出卷、不持有管理员或迁移凭据。失败退出后保留审计源与恢复副本，修复失败原因并重新执行；只有业务核验通过后才制定切换步骤。

### 目标宿主隔离容器演练

目标主机 root 执行 `bash deploy/scripts/verify-recovery-tool.sh /var/backups/my-bill/daily/YYYY-MM-DD.cms my-bill-recovery:已核对源码提交号`。先从对应源码用 `docker build -f server/Dockerfile --target app -t my-bill-recovery:提交号 .` 构建工具镜像并记录镜像 ID；镜像标签只接受 7—40 位十六进制提交号。

脚本校验归档 SHA256，解密数据库及同一归档的 exports 到 0700 临时目录，建立独立 internal 网络、无宿主端口的临时 PG 与随机凭据；保留对象原所有权和授权，应用仅用 app 角色连接恢复库。随后运行保全、重放及重复重放，核对账目条数和金额，退出清除本次容器、网络及明文目录。最多使用 PG 768MiB 与工具 768MiB 内存、PG 2GiB tmpfs；不足时失败，不能直接切向线上资源。运行期间短暂消耗额外资源，应避开宿主其他业务高峰。

这里保全的是**归档恢复副本**中的审计，用于验证目标宿主的工具链与权限，不证明已保全备份后新发生的注销；真实恢复仍须先从维护窗口中的当前库保全最新审计。若归档没有账目，脚本明确输出 LIMIT，不将空库验证计作代表性业务恢复或 RTO 达标。匿名审计会使恢复副本应删数据减少，若前后总额变化，脚本中止自动通过并要求按重放结果人工对账；不得改为忽略差异。

追加 `--synthetic` 可演练固定业务规模，例如：

```bash
bash deploy/scripts/verify-recovery-tool.sh /var/backups/my-bill/daily/YYYY-MM-DD.cms my-bill-recovery:提交号 --synthetic
```

此模式只在本脚本创建的专用临时库中执行 `server/src/test/resources/recovery/recovery-business-fixture.sql`；库名、空账目与显式会话标记均须满足。创建三个合成租户、各一万条支出和一个导出文件，保存数据库/文件快照，模拟快照之后发生的第三租户注销并独立保全审计，再重建临时库、还原文件、核对哈希、验证两租户 RLS，最后重放注销两次。断言保留两万条支出、金额 493600.00、两个原样导出文件及已注销账号不存在。常驻业务库没有写入。

这证明该样本规模下的数据/文件恢复及注销链路，不证明所有未来数据量、收入/调整/回收站页面或人工入口切换耗时。实际运行须同时记录样本规模、自动化耗时、异常和最终健康，不能只报一个“RTO 已通过”。恢复容器必须显式设置 `MY_BILL_EXPORT_DIRECTORY` 与挂载路径一致；缺失配置会触发路径保护，不能关闭保护规避。

备份脚本将历史 `last-success` 的宿主偏移时间规范成 UTC 后发布状态，RUNNING/FAILED 同样携带可解析的最近成功时间。巡检允许最近成功未超过 26 小时、当前运行未超过一小时的 RUNNING；失败、过期或未来时间仍告警，避免正常备份期间误报。

### 恢复后的服务与入口验证

`--synthetic` 只接受恢复后账目为空的项目基线归档，非空归档由 fixture 门禁拒绝，不能为演练清空真实业务库。

`verify-recovery-tool.sh <归档> <恢复镜像> --synthetic` 在既有隔离数据/文件恢复和注销重放之后，启动连接临时库的普通应用与临时 Caddy，再调用 `verify-recovery-http.py` 检查入口切换/回退、两账号登录、报表/明细/下载、跨租户拒绝、退出及注销账号拒绝。Python 脚本仅由该演练入口调用，宿主统一要求 Python 3.8+；不会连接生产代理。样本账号使用公开测试密码，只存在于有库名、空账目和显式标记保护的临时库，退出即销毁。脚本不开放宿主端口，应用只挂载本轮随机运行角色密码与导出副本。

该验证证明隔离环境的恢复业务和切换链路；真实事故仍由运维按上文保全审计、恢复、验证、切换生产入口。具体耗时与规模见部署案例，不将测试总耗时直接等同于含人工响应时间的事故RTO。
