# 开发计划

- 目标与范围：

  将“我的账单”改造为仅供 iPhone 安装的离线 iOS App，保留现有记账、字典、模板、调整、回收站、明细和报表能力，移除联网账号、网页发行、服务端及部署体系，补齐适用的设计契约、原生存储、备份恢复和 CI。用户已于 2026-11-15 授权按本计划开始实施：先执行阶段 0，各阶段验证及自审完成后依次推进；不迁移旧账本，不恢复已停止的日常 Web 服务。

  用户明确认可现有交互页面，本次以原页面源码、布局、视觉风格和操作路径为迁移基准，保留现有页面与组件。改动集中于本地数据、原生设备能力及必要 iOS 适配，不开展整页/组件体系重写、导航重排、换主题或以“优化体验”为由重新设计。详细保护范围及必要适配边界见 [S4](#s4页面复用与-stock-规则的适配)。

- 来源与模式：普通模式。直接承接用户“先制定详细计划、待确认单列、暂不开发”、七项决策答复、补齐配置保护/数据库兼容/性能门禁的要求，以及最新“原有交互页面相对满意，不要重构”的约束；[前置开发技术指引原文](pre-development-technical-guide.md)保持不变。引用[原有需求](../initial-development/requirement.md)、[项目规则](../../AGENTS.md)、[DESIGN](../../DESIGN.md)及现有实现。已有手机页面、组件和 DESIGN 是本次 UI 迁移基线；新增备份、恢复和清空沿用原有设置组件与风格，本轮不另建原型或 PRD。

## 1. 需求与交付总览

- 总体业务说明：

  使用者是本机账本的持有人，首次打开即进入“记一笔”，无需账号和网络。有效输入经本地应用服务校验，在 SQLite 事务中保存账目及相关最近值，明细与报表消费同一有效状态；退款、报销冲减原支出。删除、恢复、商品合并和重启都不能破坏关联与统计。用户从“我的”主动导出、备份或恢复；失败保留原任务和可用数据。

  L1—L11 是本计划使用的本地目标编号，不冒充正式 PRD 编号；L11 承接用户后续“原有交互页面相对满意，不要重构”的明确要求。R1—R72 沿用原需求编号并逐项映射；“保留”表示迁移后保持业务行为，不表示已经在 App 实现。“替换/退役”是本次纳入的改造动作；原联网能力不再建设。后续建议与原排除项不因改造自动纳入。覆盖判断描述计划承接，实际通过只由第 4 章证据决定。

## 2. 总体实施方案

- 整体思路：

  以下按 D01 已确认的混合 App 路线规划，T2 已验证最小原生组合及指定真机骨架出口：将现有 Vue 界面逐步迁至 app/src；本地应用服务、领域规则和 Repository 接替 HTTP API；原生桥接只承接设备数据库、文件及系统能力。正式资源全部进入安装包，不配置远程 server.url、不保留常驻本地 HTTP 业务服务。CI 从原生最小验证起建立，每个业务任务同步接入，T15 验证完整执行协议，T16 最后移除旧工程。

### S3：数据、金额与生命周期共同契约

- 用途与适用任务：

  适用于 T3、T5—T12、T17，保证移除服务端后仍保持同一业务解释。旧约束以[原需求第 6 章](../initial-development/requirement.md#6-核心业务规则)和基线服务/Mapper 测试为来源；T13 已按 D04 排除。

- 方案与关键契约：

  1. 本地只管理一份个人账本，不建立伪账号、伪租户或角色表；账本元信息保存应用维护的 schemaVersion、datasetId、初始化完成标记、seedVersion、创建时间和已知历史覆盖起点。新账本以创建时间为基础，恢复时保留可信的原覆盖元信息；不能将最早一笔账目自动当作完整历史起点。结构版本、初始化来源和外部备份格式的职责见下文。
  2. 稳定业务 ID、名称规范化键、历史名称快照、启停状态、排序和 rowVersion 继续存在。商品及模板名称执行 NFKC、去首尾空白、折叠连续空白、英文小写；商品合并影响引用、模板业务键和最近值时同事务处理。默认配置与用户修改按下文保护规则管理，升级不得重铺默认清单。
  3. 单价 4 位、数量 3 位、金额 2 位，上限和 ROUND_HALF_UP 保持现状。推荐数据库存储在有界整数范围内的缩放值，传桥与公共 DTO 使用十进制字符串，计算使用 BigInt/精确十进制。T2/T3 必须证明参数绑定、查询回传、累计值超过 JS 安全整数及数据库整数边界时的行为；必要时分批精确聚合，不能用 SQLite REAL 或浮点 AVG 替代业务精度。
  4. 账目、最近值和幂等结果共同提交；相同操作 ID、相同规范化内容返回同一结果，内容不同时返回冲突。编辑使用版本条件更新；缓存页面也可能持有旧版本，不能因单设备取消冲突防护。写失败或取消不得留下半笔记录、悬空引用或成功反馈。
  5. 发生时间以带偏移时刻保存，业务日期按 Asia/Shanghai 生成。未来时间校验改用注入的设备时钟 +5 分钟；设备时间被调整后不得重写既有业务日期。阶段 0 冻结清理保护：相较上次观测回退超过 5 分钟、同进程墙钟与单调时钟的经过时间相差超过 5 分钟，或跨启动间隔达到 30 天时，跳过本轮自动永久清理并显示现有提示组件承载的延期原因；缺少观测基线时先记录样本，不自动永久清理。同一前台轮次不自动重试，后续前台轮次重新检查；用户主动的二次确认永久删除路径保留。只检测可观测时钟异常，不承诺识别首次使用前已错误且不再跳变的设备时间，也不依赖联网校时。
  6. 退款/报销只从有效支出上下文创建，有效累计不超过实付；删除支出冻结关联调整并退出统计，恢复时重新验证；永久删除不得留下调整孤儿。回收站保持 30 天业务窗口，到期清理在启动/回到前台执行有界批次，不把关闭 App 后的调度记为准时完成。
  7. 统一过滤模型供明细、报表和 CSV 消费。有效收入、原始支出、有效冲减、净支出、结余保持原公式；不同单位的商品数量和单价分别分析，金额可汇总。图表可为绘图位置转换数值，但所有展示金额、标签和导出继续消费精确结果。
  8. 本地维护操作有明确的进行中、成功、失败、取消或中断状态；备份文件完成、校验且可读取后才成功。数据目录、临时目录、用户选中文件和 Keychain 命名空间分开，清理只作用于本 App 所有的对象，不删除 .local/web、外部副本或其他 App 数据。

  默认配置与用户修改保护（T3、T5、T7、T12、T17 共用）：

  默认字典和初始偏好由仓库中的版本化 seed 维护，随安装包发布；用户实际使用的字典、排序、启停及偏好保存在 SQLite。管理员默认字典接口不进入新 App。seed 只在明确的新数据集初始化时落库，与初始化完成标记、seedVersion 共同提交；失败不得留下“已初始化”的半成品，重复启动不得重复插入。不能以某张字典表为空判断是否需要重新初始化。

  已有业务数据而元信息缺失时，只允许已知历史版本的明确迁移补齐元信息；无法解释的状态进入拒绝/恢复路径，不能猜测为新库并重铺默认值。

  | 情况 | 生效规则与用户数据保护 |
  | --- | --- |
  | 首次安装或确认清空后建立新账本 | 使用该安装包的当前默认清单；保留稳定默认项标识和来源版本，初始化成功后才开放业务写入 |
  | 用户新增、改名、排序、停用或删除允许删除的默认项 | 保存本机结果；引用和历史名称快照遵循既有规则，不因重启或升级被还原、重新启用或重新生成 |
  | 后续 App 修改默认名称、顺序、启停或新增推荐项 | 影响之后建立的新账本；已有账本不自动同步整套新 seed，不因 seedVersion 不同重置用户配置 |
  | 新功能必须为已有账本增加基础数据或偏好字段 | 新增独立、带版本的数据迁移，声明稳定键、适用旧版本、预期影响和冲突处理；新增偏好仅对真正缺失字段采用已定义默认值，保留已有合法的 false、0、空值等用户选择 |
  | 迁移中新必需项与已有项重名或键冲突 | 按迁移预先定义并验证的映射/拒绝策略处理；不得按显示名称擅自覆盖、合并或重新启用用户项，冲突未解决则不提交迁移 |
  | 从 App 备份恢复 | 保留备份内的字典、偏好、seedVersion 和初始化状态；先兼容升级，再恢复用户数据，不灌入当前安装包默认清单覆盖它们 |

  保护样本使用默认资金渠道“现金”：用户改为“零钱”、调整排序并停用，同时新增自定义项、保留历史引用；新包将原默认名称改为“现金钱包”并新增推荐项。已有账本必须保留“零钱”、用户顺序、停用状态、自定义项、稳定 ID 及历史快照；独立新账本采用新包默认清单。此样本由 V3-T4/V5-T3 做数据断言，由 V17-B2 在覆盖安装的真实页面检查。

  数据库版本与升级兼容（T3、T12、T17 共用）：

  | 版本或标记 | 职责与变化规则 |
  | --- | --- |
  | schemaVersion 与迁移履历 | 应用数据库结构及必要数据转换版本；记录迁移编号、摘要和完成状态，与成功迁移结果一致，不使用 App 版本号或 SQLite 引擎自身结构计数替代 |
  | seedVersion 与初始化完成标记 | 记录该数据集初始化所用默认配置；普通 App 升级不将其改成当前 seed 版本，不把用户修改误判为初始化缺失 |
  | backupFormatVersion | 外部完整备份的封装、清单与加密格式版本；恢复时同时检查其兼容范围和内部 schemaVersion，不能只看文件扩展名 |

  每次存储结构、字段语义、必需基础数据或持久化偏好变化均新增有序迁移；已经发布的 SQL、数据步骤、版本化算法及摘要不可改写，修正另加新迁移。每个已发布数据库版本保留到当前版本的升级路径，支持用户跳过 App 版本直接更新；首次发布前以旧版夹具验证，发布后按真实已发布版本清单扩充。D04 取消旧 Web 导入不影响本 App 自身的版本升级与备份兼容。

  启动/恢复入口取得数据生命周期操作权后，按“检查版本与空间 → 生成可读取的升级前保护快照 → 执行待应用迁移 → 校验结构、外键、对象数量、精确金额和引用 → 提交相应版本/履历 → 开放业务读写”执行。普通变更在事务中完成；需重建表或临时新库时显式映射旧字段，重建必要索引和约束，完成校验后才切换可用库。迁移成功前阻止录入、草稿回写及其他消费者访问半升级状态；共享原生迁移器同时服务正常启动和旧备份恢复，避免维护两份转换逻辑。技术参考：[SQLite 结构迁移](https://sqlite.org/lang_altertable.html)、[原子提交](https://www.sqlite.org/atomiccommit.html)，实际语法以 T2 锁定的原生 SQLite 版本验证为准。

  任一步失败或进程中断均不得自动删库/重建。以事务及持久化切换状态识别未完成工作，保留旧库/保护快照并提供重试或恢复结果；已完成迁移不得重复应用。快照创建失败、空间不足、未知迁移摘要或版本断档时停止依赖写入。旧 App 打开更新的 schemaVersion、或遇到超出支持范围的备份格式时明确拒绝写入/恢复，不静默丢弃新字段；回退先验证兼容性，优先向前修复，使用旧快照回退须明确其后的新增数据不在该快照内。

  旧备份在独立临时库解密与校验，通过同一迁移链升至当前结构，并核对用户字典、草稿、回收站和金额后才按 D06 整库替换；未知更高版本拒绝且保留当前库。新装、逐版本升级、跨版本升级、重复打开、失败回滚、中断重开、旧备份恢复和新版本拒绝均是必要验收分支，不能以空库建表通过替代。

### S5：逐阶段 CI、证据与数据隔离

- 用途与适用任务：

新装无个人数据的验收容器可以按本轮资源生命周期清理；已有数据的覆盖升级只使用已验证的安全备份或向前修复。旧二进制回退前必须验证 schema/备份格式兼容，不假定安装旧包能降库；不同签名身份导致的数据访问风险先停止并核对，不通过卸载补救。清空/恢复的不可逆边界已在 T12 明示，用户外部副本不自动擦除。
