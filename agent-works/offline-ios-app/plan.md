## 1. 需求与交付总览

- 总体业务说明：

  使用者是本机账本的持有人，首次打开即进入“记一笔”，无需账号和网络。有效输入经本地应用服务校验，在 SQLite 事务中保存账目及相关最近值，明细与报表消费同一有效状态；退款、报销冲减原支出。删除、恢复、商品合并和重启都不能破坏关联与统计。用户从“我的”主动导出、备份或恢复；失败保留原任务和可用数据。

- 共同范围与覆盖判断：

  L1—L11 是本计划使用的本地目标编号，不冒充正式 PRD 编号；L11 承接用户后续“原有交互页面相对满意，不要重构”的明确要求。R1—R72 沿用原需求编号并逐项映射；“保留”表示迁移后保持业务行为，不表示已经在 App 实现。“替换/退役”是本次纳入的改造动作；原联网能力不再建设。后续建议与原排除项不因改造自动纳入。覆盖判断描述计划承接，实际通过只由第 4 章证据决定。

## 2. 总体实施方案

- 整体思路：

  以下按 D01 已确认的混合 App 路线规划，T2 已验证最小原生组合及指定真机骨架出口：将现有 Vue 界面逐步迁至 app/src；本地应用服务、领域规则和 Repository 接替 HTTP API；原生桥接只承接设备数据库、文件及系统能力。正式资源全部进入安装包，不配置远程 server.url、不保留常驻本地 HTTP 业务服务。CI 从原生最小验证起建立，每个业务任务同步接入，T15 验证完整执行协议，T16 最后移除旧工程。

### S3：数据、金额与生命周期共同契约

- 用途与适用任务：

  适用于 T3、T5—T12、T17，保证移除服务端后仍保持同一业务解释。旧约束以[原需求第 6 章](../initial-development/requirement.md#6-核心业务规则)和基线服务/Mapper 测试为来源；T13 已按 D04 排除。

  1. 本地只管理一份个人账本，不建立伪账号、伪租户或角色表；账本元信息保存应用维护的 schemaVersion、datasetId、初始化完成标记、seedVersion、创建时间和已知历史覆盖起点。新账本以创建时间为基础，恢复时保留可信的原覆盖元信息；不能将最早一笔账目自动当作完整历史起点。结构版本、初始化来源和外部备份格式的职责见下文。
  2. 稳定业务 ID、名称规范化键、历史名称快照、启停状态、排序和 rowVersion 继续存在。商品及模板名称执行 NFKC、去首尾空白、折叠连续空白、英文小写；商品合并影响引用、模板业务键和最近值时同事务处理。默认配置与用户修改按下文保护规则管理，升级不得重铺默认清单。
  3. 单价 4 位、数量 3 位、金额 2 位，上限和 ROUND_HALF_UP 保持现状。推荐数据库存储在有界整数范围内的缩放值，传桥与公共 DTO 使用十进制字符串，计算使用 BigInt/精确十进制。T2/T3 必须证明参数绑定、查询回传、累计值超过 JS 安全整数及数据库整数边界时的行为；必要时分批精确聚合，不能用 SQLite REAL 或浮点 AVG 替代业务精度。
  4. 账目、最近值和幂等结果共同提交；相同操作 ID、相同规范化内容返回同一结果，内容不同时返回冲突。编辑使用版本条件更新；缓存页面也可能持有旧版本，不能因单设备取消冲突防护。写失败或取消不得留下半笔记录、悬空引用或成功反馈。
  5. 发生时间以带偏移时刻保存，业务日期按 Asia/Shanghai 生成。未来时间校验改用注入的设备时钟 +5 分钟；设备时间被调整后不得重写既有业务日期。阶段 0 冻结清理保护：相较上次观测回退超过 5 分钟、同进程墙钟与单调时钟的经过时间相差超过 5 分钟，或跨启动间隔达到 30 天时，跳过本轮自动永久清理并显示现有提示组件承载的延期原因；缺少观测基线时先记录样本，不自动永久清理。同一前台轮次不自动重试，后续前台轮次重新检查；用户主动的二次确认永久删除路径保留。只检测可观测时钟异常，不承诺识别首次使用前已错误且不再跳变的设备时间，也不依赖联网校时。
  6. 退款/报销只从有效支出上下文创建，有效累计不超过实付；删除支出冻结关联调整并退出统计，恢复时重新验证；永久删除不得留下调整孤儿。回收站保持 30 天业务窗口，到期清理在启动/回到前台执行有界批次，不把关闭 App 后的调度记为准时完成。
  7. 统一过滤模型供明细、报表和 CSV 消费。有效收入、原始支出、有效冲减、净支出、结余保持原公式；不同单位的商品数量和单价分别分析，金额可汇总。图表可为绘图位置转换数值，但所有展示金额、标签和导出继续消费精确结果。
  8. 本地维护操作有明确的进行中、成功、失败、取消或中断状态；备份文件完成、校验且可读取后才成功。数据目录、临时目录、用户选中文件和 Keychain 命名空间分开，清理只作用于本 App 所有的对象，不删除 .local/web、外部副本或其他 App 数据。

- 对应需求与约束：L3；R8、R14、R39 等共用规则

- 输入与前置依赖：

  T2 验证通过的原生数据库组合；S2、S3，现有 money.ts 与 LedgerWritePolicy、BusinessDateRange 和数据库迁移作为行为依据。

- 任务状态：🟢 已完成

- 目标与现状依据：

  以版本化 SQLite 和单一领域实现接替 PG 的精度、约束和事务基础；为后续应用服务提供稳定接口。

#### 实现设计

- 实施方案：

  拟建数据连接管理、事务单元、schema 迁移、seed 版本、Repository 入口及本地错误模型。统一账目/字典/模板/调整的 ID、快照、rowVersion、引用与索引；只增加后续任务需要的结构。迁入并扩展现有 BigInt 金额工具及时间/文本规则。初始化与升级分开，升级前做安全快照，未知更高版本拒绝写入，失败保持旧库可恢复，不能自动删库重建。

  具体版本和保护契约统一消费 [S3](#s3数据金额与生命周期共同契约)：在拟新增 app/src/data/migrations、seed 和元信息 Repository 实现初始化完成标记、seed 来源及不可改写的迁移履历，版本不匹配先进入明确的初始化/升级/拒绝状态。正常启动与 T12 恢复调用同一迁移器；已初始化的空字典和用户删除项不触发补种，结构和必需数据迁移共同遵守用户配置保护规则。

- 影响与保持项：

  后续所有应用服务消费同一连接与事务骨架；前端原有纯函数只保留一个权威入口。移除 tenant_id 的含义由本地账本作用域承接，不保留假身份。

- 性能、安全与兼容：

  精确核对 JS 安全整数和 SQLite 整数边界、聚合溢出、外键开启、事务隔离、串行写入队列的上限与取消。按 D05 在数据库、内部快照及其私有目录创建/替换后设置并回读排除系统备份标记，升级前保护快照复用同一原生能力；自动快照策略见 T12。可移植备份按已确认 D06 在 T12 实施加密，不能将文件标记核验扩大为备份恢复已通过。

- SQL与数据变更：

  拟新增 app/src/data/migrations/0001_initial.sql 及测试用升级夹具；执行者是 App 的版本迁移器，目标仅本 App 沙盒。旧 Flyway 不改校验和、不直接在 PG 运行 SQLite 脚本；失败回滚/文件切换有状态标记，重复启动不重复 seed 或升级。

  每份新迁移声明前置 schema、字段映射/缺省值、用户值保持、校验和中断处理；维护真实已发布 schema 清单与对应旧库夹具。新装和跨版本升级都必须到达同一目标结构，所有迁移中“执行结果+完成履历”一致提交；禁止以删除用户库或改写已发布脚本修复校验失败。

#### 执行安排

- 开发步骤与产出：

  1. 从现有迁移确认实际字段、类型、约束和历史快照，形成有测试消费的本地模型。
  2. 实现精确数值、时间和本地错误，再实现版本守卫、事务、参数化 SQL 与 Repository 公共入口。
  3. 用真实 iOS SQLite 执行新装、每个已发布版本直接升至当前、故障回滚、重跑和不兼容版本拒绝；覆盖缺少标记、初始化中断、空字典和新 seed 不覆盖用户值，执行 V3-T4。
  4. 将迁移/seed 及共享数据入口变化绑定 database 专项和旧版本矩阵；普通 TS 测试与原生测试都接入最小 CI，不能等最终打包才检查兼容。

- 风险与未决：

  不能把数据库声明为 NUMERIC 就视为精确十进制；不能仅测内存库，也不能因单设备省略版本和重复提交边界。

#### 完成与结果

- 完成条件：

  V3-T1—T4 通过；初始化、升级及拒绝路径符合 S3，旧版本矩阵有真实原生证据。本任务是基础能力技术验收，完整业务由后续 V5—V12 证明；V13 已排除。

- 实施结果：

  LedgerDatabase 已统一持有原生连接及读写/生命周期队列，提供原子初始化、版本迁移、幂等与精确金额基础。新装事务中当前 seed 优先于同键迁移缺省；存量库不重铺字典或偏好，合法 false/0/空值保持。每个迁移版本携带完整 schema 清单及摘要，按对象归属和 SQL 词法比较并保留字符串/词边界；结构不符、版本断档或未知高版本明确拒绝；快照、DDL、数据步骤及履历按既定边界恢复。

  正式升级的三个中断边界均由生产 open→upgrade 路径承接；测试观察器和故障控制不进入生产包。非热 journal 仅在完整头的 magic 清零且 SQLite 校验通过后放行，热日志、短头和非空 WAL 继续拒绝。资源门禁使用 TypeScript 解析器检查已知 Web 存储/WASM 访问，不将静态检查扩大为任意动态访问证明。受控旧库兼容范围见 [V3](#v3数据新装升级与数值基础)；完整备份恢复及真机文件保护/容量仍由 T12、T14/T17 承接。

#### 实现设计

- 实施方案：

  Expense/Income 本地应用服务校验字段和有效字典，记录业务时间/日期、金额、快照、版本及操作 ID，并在同一事务更新账目、最近值和幂等结果。支出保持单价×数量的计算金额和可手改实付；收入保持名称、付款方、分类、金额和收款方式，不用虚拟商品。编辑复用表单，版本冲突保留输入并提供重新加载/确认入口；重复提交返回同一保存结果。

  2. 接通创建、编辑、连续录入、保存摘要和适用撤销；核对字段切换不会误提交另一类型。
  3. 测试重复点击、提交后未收到确认即重启、旧版本编辑、字典失效及磁盘/事务故障；执行 V6。

  数据库写入完成但 UI 未收到结果时，重试必须查回原结果；单设备缓存页面仍可能引发旧版本覆盖。

#### 实现设计

- 实施方案：

- 影响与保持项：

  新增数据管理页面/面板复用 SettingsGroup、AppDrawer、AppDialog、AppStatusNotice 和进度反馈，主滚动区承载详情，危险确认与取消保留原任务。恢复/清空必须取消旧查询和草稿写回，重置图表与页面缓存；切换数据集的事务须处理恢复草稿的归属，页面缓存随 datasetId 重建。

- 性能、安全与兼容：

  使用数据库一致性快照/备份接口或安全关闭与 checkpoint，不只复制运行中的主 DB 文件而遗漏 WAL。文件采用原子发布、大小/版本/压缩展开边界、校验及受控临时目录；密钥不入日志或普通偏好。内部数据库、快照与临时副本在创建/替换后核验排除系统备份标记；用户主动导出的外部文件由所选存储位置管理，不改写其资源属性。后台时间不足时取消/延期并留状态，不假报完成，也不承诺关闭 App 后的定时任务。

- SQL与数据变更：

  维护 backup/restore/clear 的最小操作状态和新旧数据集切换标记；恢复仅写临时目标库，所有校验通过前不覆盖当前库。中断后以切换标记收敛文件补偿，重复恢复/清空不会产生混合数据集。追加 [0009 CSV 索引](../../app/src/data/migrations/0009_csv_export.sql)及对应结构清单，由共享迁移器在 v8→v9 或新装事务执行；仅新增账目/调整的稳定导出排序索引，不更改既有迁移、业务内容或 seed。失败整笔回滚，保留保护快照，重开按履历重试。

  备份清单同时保存 schemaVersion、初始化标记、seedVersion 和 backupFormatVersion；旧 App 备份先在临时库调用 T3 的共享迁移器，校验用户配置及全部对象后再切换。新版本/未知格式必须在替换前拒绝，外部备份和当前库保持可用。清空明确创建新 datasetId，以当前 seed 初始化新账本；普通恢复不走此分支。

#### 执行安排

- 开发步骤与产出：

  1. 冻结格式、保护与清空范围，定义创建、取消、失败、成功及中断恢复状态；补文件适配器。
  2. 接入 CSV 与完整备份，验证导出完成后系统文件确实可读取；分享取消不得删除原账本。
  3. 实现临时库恢复、确认切换、缓存重建和有界旧文件回收，再实现清空事务/文件补偿。
  4. 在安装版覆盖损坏、错误密码、低空间、取消、切后台和替换中断，并用每个已发布备份格式/数据库版本的受控夹具验证升级恢复及未知高版本拒绝，执行 V12-T4；保留用户字典和偏好，不用当前 seed 修补覆盖。

- 风险与未决：

  数据库加密不自动提供跨设备可恢复备份；系统备份、App 内快照和用户外部副本的保留规则必须分开。备份密码丢失时无法恢复对应文件；格式 1 已冻结系统 PBKDF2-HMAC-SHA256 与 AES-256-GCM、大小/参数及认证错误语义，具体机制见[数据管理架构](../architecture/architecture-decisions.md#离线-ios-原生入口)；篡改、错误密码及恶意参数必须拒绝。不能借“清空”擦除用户外部文件或 Web 资料。

#### 完成与结果

- 完成条件：

  V12-T1—T4、V12-B1—B3 通过；完整恢复逐对象、关键值、用户配置和报表核对一致，跨版本恢复及拒绝路径有证据，失败时原账本可用。

工作目录为本仓库根目录。当前按验证规范先运行最低充分的局部检查，只有影响范围必要且符合失败锁/证据条件时才进入对应完整检查；不为文档变更或无新证据重复完整验收。已有 `npm run check:app` 执行类型/测试/资源检查，`npm run build:ios-app` 在共享链路中构建 Vue 资源、执行 Capacitor 同步并编译未签名 Release；原生完整入口已包含公共检查，不再为同一轮单独重跑。命令来源为 [package.json](../../package.json)、[App 脚本](../../scripts/ios-app.sh)及 app/package.json 的 native:sync，与[官方同步流程](https://capacitorjs.com/docs/basics/workflow)一致。

最终工程候选沿用 `npm run ci:ios-app -- plan final` 及同一入口的 run/result 对账，准确参数与数据准备引用验证规范；日常仍不为取得集中报告重复已充分的局部检查。现有 final 已包含覆盖率、原生恢复及两种规模模拟器观测，仍须按 S5 完成同轮实际结果对账，不用工程/模拟器范围冒充真机性能与安装交付。尚未构建安装的候选不要求先有真机报告；签名安装后在 I5 执行已登记的可信手动 install-gate。

本轮 JS 资源、原生构建/测试结果与最终提交绑定，检查所有实际选择的套件、原生测试和报告；缺项/失败停止，不把单次构建替代业务验收。拟定正式制品落点为 .local/ios/releases/<源码提交>/<版本-构建号>/，构建缓存和测试临时资源不作为交付物提交。签名步骤若重新构建资源，必须复核资源摘要和相同源码配置，避免测试与安装包漂移。

SQL 操作索引：T3 的 app/src/data/migrations/0001_initial.sql 已产出并通过原生验证，后续结构变化追加编号迁移及对应版本结构清单，由 App 迁移器在 I4 自动执行，按已锁定版本序列校验，不人工重复运行；T5—T12 所需查询/约束归对应任务及有版本说明的迁移。T13 已排除，不执行旧账抽取或转换。现有 PG 迁移、角色文件和服务器 schema 在此路径完全不执行。

#### I3：归档、签名与制品核验

使用 T2 已核实的 Xcode scheme/原生管理方式，T17 交付的归档入口从同一源码和资源生成构建，记录 C1/C2 的实际身份及版本。Development 路径由 Xcode 安装到指定设备，交付工程及可复现步骤；登记设备分发路径才按资格和 profile 导出适用的 IPA。[Apple 免费账号说明](https://developer.apple.com/help/account/basics/about-your-developer-account)规定 Personal Team 配置 7 天到期；[登记设备分发](https://developer.apple.com/documentation/xcode/distributing-your-app-to-registered-devices)要求匹配签名及设备范围。两者都不能承诺一次安装永久有效。

核对源提交、App/构建版本、Bundle ID、签名有效期、目标设备范围、资源摘要和最终制品摘要；确认 Release 无远程 server.url、调试写开关、个人数据或私钥。证书/私钥仅在受控签名环境存在，结束后按其生命周期保管/清理，不能随 IPA 或源码分发。失败保留必要脱敏诊断，不改签名身份或降低校验强行安装。

#### I4：新装、覆盖升级与条件导入

先在独立验收容器验证新装的 C4 迁移/seed，再以同一身份覆盖含已知数据及用户字典/偏好修改的早期原生候选；不卸载旧 App 来回避升级测试。第一次打开时观察版本迁移/失败恢复，核对 schema/迁移履历、初始化来源、账目、调整、字典、模板、偏好、草稿和备份清单；完成 V17-T2 后才能继续最终业务核验，新旧默认配置的保护结果按 V17-B2 直接检查。

D04 已排除旧 Web 导入，C7 与 V13 不适用。新 App 自身备份仍按 T12 的选择文件→校验范围/版本→确认恢复→临时库构建→原子切换流程执行 V12 的恢复回读。任何失败保留源包、原 App 数据和相应备份，禁止手工补表或覆盖当前库。新装成功不能替代升级成功，恢复成功不能替代完整报表检查。

#### I5：最终离线核验与交付

在目标真机运行当前候选，退出调试连接后执行 V17-B1/B2，并复用 V6—V12 的代表链路及受影响的 V14 检查。记录实际提交、版本、设备/系统、签名方式、数据来源、操作、观察和未覆盖项；iOS 图标出现、SQLite 文件存在或 CI 绿色都不能单独作为完成证明。

签名安装后按 S5/V17-T3 核验匹配当前候选的真机报告；条件变化时先补测。然后由 T15 在现有 ci:ios-app 中登记的 install-gate 汇总 I2 的 app-common/必要专项、D07 的 1 万条硬指标及完整 10 万条观测。手机不可用或报告缺失等情况保持安装交付未完成；托管 CI 提供工程检查结果，本机可信执行提供真机结果，按同一协议汇总。该套件和可信签名检查已提供，参数与材料格式见[统一验证策略](../testing/guide.md#统一套件按需-ci-与最终验收)；真实候选签名和手机证据尚未执行，不能由协议夹具补足。

交付与 D03 相符的 IPA 或 Xcode 工程/安装材料、摘要及稳定安装/升级/备份恢复说明，说明到期后如何重新签名/覆盖安装而非默认卸载。外部上架、服务器部署和用户真实数据写入不由本计划保存自动授权。

### 失败恢复与重新放行

任一必要门禁、签名、迁移、恢复或最终业务检查失败，立即停止进入下一阶段或交付。原生库迁移/恢复失败先保留原库、临时目标和最小诊断，按 T3/T12 的切换标记判断原账本；不能反复自动重试写入或以删除库重建消除错误。源 Web 库和备份始终不修改。

新装无个人数据的验收容器可以按本轮资源生命周期清理；已有数据的覆盖升级只使用已验证的安全备份或向前修复。旧二进制回退前必须验证 schema/备份格式兼容，不假定安装旧包能降库；不同签名身份导致的数据访问风险先停止并核对，不通过卸载补救。清空/恢复的不可逆边界已在 T12 明示，用户外部副本不自动擦除。

修复后在同一实际源码/设备范围复验受影响 V 项及必要门禁，重新生成/核对制品；原失败证据与未完成项保留在本计划对应检查点，不倒改为成功。重新放行必须同时满足数据完整、业务结果、签名安装与必要 CI 证据；日常 Web 服务继续保持停止。
