# T26 性能、容量与可观测性基线

## 1. 结论与边界

本地代表性数据基线通过，未发现需要新增索引或改变第一期业务范围的问题。候选、明细与分类报表均通过真实会话进入 Spring Security、应用服务、MyBatis-Plus/Mapper XML 和 RLS，另用与 Mapper 等价的 SQL 留存 `EXPLAIN ANALYZE`；明细索引探针和到期清理候选分别命中 `idx_ledger_active_cursor`、`idx_ledger_purge_due`。51,000 行个人数据导出通过 MyBatis 游标以 200 行 fetch size 写入空输出流，没有在 Java 中构造全量集合；到期清理始终保持每批最多 100 行。

本报告是 2026-09-27 在本机 Java 21.0.10、PostgreSQL 16.14 一次性隔离集群上的单进程暖机基线，不是生产 SLA。它不包含公网/TLS 时延、多实例竞争、目标主机 CPU/内存曲线、真实磁盘告警触发、备份新鲜度或恢复吞吐；这些环境证据仍由 T29 补齐。

## 2. 可复现数据与命令

执行命令：

```bash
npm run check:performance
```

脚本只复用系统已经安装的 PostgreSQL 16+ 可执行程序，在 `mktemp` 目录创建一次性集群，建立最小权限的 `my_bill_migration`/`my_bill_app` 角色，完成后停止并删除集群。它不连接本项目开发库、其他项目数据库、Docker 或任何共享数据库。

固定合成数据：

| 数据 | 数量 |
| --- | ---: |
| 商品候选 | 2,000 |
| 有效支出 | 40,000 |
| 有效收入 | 10,000 |
| 已到期回收站账目 | 1,000 |
| 导出总行数 | 51,000 |

测试输出同时写入未提交的 `server/target/performance-baseline.json`，便于同机前后对比；业务仓库不保存机器相关的临时产物。

## 3. 本次基线

| 路径 | 本机结果 | 结构性门槛 | 结论 |
| --- | ---: | --- | --- |
| 正式商品候选 HTTP | 107.987–109.068 ms，返回 1 行 | 真实认证/RLS/Mapper 链路，服务端 `LIMIT 20` | 通过 |
| 正式明细首批 HTTP | 112.004–112.994 ms，返回 20 行 | 真实认证/RLS/Mapper 链路，服务端批量上限 20 | 通过 |
| 正式支出分类报表 HTTP | 79.052–79.157 ms，返回 1 组 | 真实认证/RLS/Mapper 链路，服务端聚合 | 通过 |
| 候选等价 SQL | 0.902–0.919 ms，返回 1 行 | 含正式关联、排序与 `LIMIT 20` | 通过 |
| 明细索引探针 | 0.040–0.047 ms，返回 20 行 | 命中 `idx_ledger_active_cursor` | 通过 |
| 40,000 行支出分类聚合 SQL | 31.022–31.284 ms，返回 1 组 | 与正式分类聚合等价，无应用缓存 | 通过 |
| 到期清理领取 | 0.065–0.067 ms，返回 100 行 | 命中 `idx_ledger_purge_due`，`FOR UPDATE SKIP LOCKED` | 通过 |
| 51,000 行 CSV 导出 | 1,141–1,150 ms | 正式 MyBatis cursor、fetch size 200、文件流式写入 | 通过 |
| 1,000 行到期清理 | 60–62 ms，11 次调用 | 正式清理任务；每批不超过 100，第 11 次确认队列为空 | 通过 |
| 数据生成和 ANALYZE | 2,712–2,881 ms | 仅一次性隔离库 | 记录，不作为产品指标 |

以上为两次本机观测范围，只用于发现数量级回退；正式 HTTP 数值还包含首次请求的安全过滤器、会话查询、序列化和 MockMvc 开销。一次完整命令的 wall time 为 13.96 秒，最大 RSS 为 379,879,424 字节（约 362 MiB）；该 RSS 包含 npm/Maven、测试 JVM 和隔离数据库工具链，不等同于常驻应用内存 SLA。后续机器、数据库参数或数据分布不同，不得直接拿这些值承诺用户响应时间；结构性门槛和索引命中才是当前稳定验收条件。

## 4. 资源上限与观测面

- Hikari 连接池默认最大 5、最小空闲 1、获取连接超时 5 秒，分别由 `MY_BILL_DB_POOL_MAX_SIZE`、`MY_BILL_DB_POOL_MIN_IDLE`、`MY_BILL_DB_CONNECTION_TIMEOUT_MS` 覆盖；默认值适配第一期单机低成本运行，T29 按目标主机与 PostgreSQL 连接预算复核。
- 明细每批最多 20；候选接口保持限量；报表使用服务端聚合且不引入缓存；导出 fetch size 200；到期账目清理每批最多 100；任务 runner 每轮默认最多 20 个任务。
- `/api/v1/health` 继续只公开最小健康结果；`/api/v1/metrics` 与 `/api/v1/prometheus` 只允许管理员会话访问，普通用户和匿名请求分别为 403/401。
- 标准指标覆盖 HTTP 状态/耗时直方图、JVM、进程、磁盘和 Hikari 连接池；有限基数业务指标覆盖登录成功/失败/限流、幂等创建/回放/冲突、后台任务结果和管理审计写入。标签不包含用户名、租户、账目文本或金额。
- `deploy/monitoring/prometheus-alerts.yml` 提供服务不可用、持续 5xx、连接池等待、任务失败和磁盘不足规则。当前只完成规则配置与语法检查，尚未接入真实 Prometheus/通知渠道，也未执行告警触发演练；T29 部署时必须按目标环境复核阈值并补证。
- Node 24 生产构建通过；主入口 JS 为 301.53 kB（gzip 99.74 kB），报表懒加载 chunk 为 575.05 kB（gzip 196.27 kB）。Vite 的 500 kB 警告来自已按路由延迟加载的报表 chunk，不增加首屏主包；当前未为消除警告而拆出脆弱的手工 chunk，后续若体积继续增长需单独治理。

## 5. 整体审查

- 正确性与一致性：性能夹具使用固定 UUID 和合成文本，测试结束随一次性集群销毁；不污染开发数据。候选/明细/报表通过正式 HTTP 和认证链路，导出与清理直接走正式实现；测试内联 SQL 只承担测试夹具和查询计划探针，不替代生产 Mapper，也不进入运行包。
- 性能与容量：未发现 N+1、无限内存集合或无界批处理；大范围报表由 PostgreSQL 聚合，完整导出使用游标，清理按固定批次重入。当前数据规模下既有索引满足首批明细和清理领取，因此没有为了“看起来优化”增加写放大索引。
- 安全与权限：指标端点不公开业务内容且默认拒绝；自定义指标只使用固定 outcome、operation、job type、action 等有限集合。Prometheus 采集授权和网络隔离仍需 T29 的目标环境方案，不在 T26 伪造完成。
- 阶段边界：T26 未修改页面、API 业务合同、业务 SQL、migration、seed、菜单或权限表；未进入 T27 安全专项或 T29 生产部署。
- 未执行项：T26 没有页面改动，因此未重复浏览器截图/交互；没有目标生产主机、Prometheus/通知渠道或生产网络，故未执行目标主机资源曲线、真实告警触发、境内网络与备份恢复。这些项目按计划保留 T29，不记为本地通过。
