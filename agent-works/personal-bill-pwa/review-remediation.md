# 个人账单 PWA 需求复核与整改报告

## 1. 本轮结论

本轮以提交 `52d6604` 为复核基线，接受“报表存在双状态源、认证成功与密码安全未闭环、一期操作缺少页面承载、下钻展示内部枚举、上一版报告证据不完整”的审查结论，并扩大检查到筛选取消、角色跳转、高影响管理操作确认、操作日志和动态控件。

整改和重新验证后：**本轮指出的 3 项 P1、2 项 P2 已关闭；当前需求与交互原型具备进入开发计划的条件。** 该结论只覆盖当前六页原型和正式需求约定的计划输入，不把原型行为等同于生产系统验收。

## 2. 未变化的需求事实

- B6：分类最多两级，一级必填、二级选填。
- B7：购买渠道选填，未填写统一展示“未指定”。
- B8：第一期仅人民币，业务时区为 `Asia/Shanghai`。
- B9：调整支持未关联入口；关联调整随原支出冻结、恢复或联动永久删除。
- 第一期仍为 55 项必须需求；必须、建议、暂不实现及开发顺序没有变化。

本轮没有改变字段、角色、范围、需求编号、设计 token 或稳定交互契约，因此 `requirement.md`、`requirement-closure.md` 和 `DESIGN.md` 无需修改。

## 4. 举一反三整改

- 筛选弹层现在区分“草稿”和“已应用状态”：取消弹层不会改变页面统计口径，再次打开会从已应用状态恢复。
- 登录除网络失败外补充系统失败反馈；失败时保留输入，不制造成功跳转。
- 停用、恢复和重置密码增加二次确认；停用、恢复、注销、重置密码、默认字典保存/排序/状态变化都会新增可查看操作日志。
- 静态用户行和动态创建用户行共用详情与“更多”操作绑定，避免第二条演示数据或新建数据缺少管理能力。
- 初始商品与动态新增商品共用同一字典行工厂；商品行在通用改名、排序、停用/恢复基础上增加合并动作。
- 初始默认字典行和动态新增行共用编辑、排序、停用/恢复绑定，避免新增后无法继续维护。

## 7. 原型边界

- 原型使用演示账号约定验证角色跳转；生产实现必须使用认证响应中的服务端角色与权限，不得根据用户名判断角色。
- 原型用本地代表性弱密码模式证明拒绝交互；生产实现必须在服务端使用受维护的常见/泄露密码数据源，并避免在客户端暴露完整密码库。
- 用户注销在原型中进入“注销处理中”；生产实现仍需后台任务、幂等、审计、数据保留/清理和失败恢复。
- 商品合并、默认字典排序和操作日志在原型中验证交互结果；生产实现必须补租户隔离、版本冲突、事务和不可抵赖审计。
