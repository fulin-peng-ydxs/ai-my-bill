# 个人账单 PWA 需求复核与整改报告

## 1. 结论

本轮按第三方审查意见重新检查了需求闭环、正式需求、DESIGN、六个页面原型、共享样式与脚本，并扩大到同类交互、状态隔离、需求追溯和开发门禁。

整改后结论：**本轮审查指出的 P1/P2 已关闭，55 项第一期必须需求可进入开发计划**。后期增强仍按建议范围独立立项，不混入第一期承诺。

## 2. 阻塞决策闭环

以下决策于 2026-08-13 获得用户确认，并作为阶段 0 已关闭门禁同步到需求闭环、正式需求、原型和验收：

| 决策 | 已确认口径 | 落地结果 |
| --- | --- | --- |
| B6 分类结构 | 最多两级；一级必填、二级选填 | 数据边界、填报/编辑、字典、分类报表和验收使用同一结构 |
| B7 购买渠道 | 选填，默认“未指定” | 空值统一显示“未指定”，不创建伪字典项 |
| B8 货币与时区 | 第一期人民币、`Asia/Shanghai` | 业务日期、日周月聚合和页面口径固定，不随设备时区漂移 |
| B9 调整生命周期 | 明细有未关联入口；原支出入回收站时调整冻结，恢复后重生效；不得留下孤立调整 | 补齐待归类创建、冻结/恢复、阻止单独永久删除和原子联动删除 |

## 4. 举一反三新增修复

- 支出原型仍残留“购买渠道必填待确认”，与 B7 冲突；已改为明确选填。
- 支出填报和编辑仍用单一“支出分类”控件承载两级结构；已拆为一级必填和二级选填，并补消费时间、单位等字段必填校验。
- 资金渠道管理抽屉仍有两个只弹提示的入口；已收敛为前往真实字典管理视图。
- 新增字典项曾使用字符串拼接插入用户输入；已改为 `textContent` 组装节点，避免原型传播不安全实现方式。
- 管理端旧 HTML 依赖启动脚本把 `data-toast` 动态伪装成真实控件；已直接重写为明确行为锚点，静态审查和运行时行为一致。
- 区域 empty 文案原先仍统一指向“去记一笔”；现按报表、明细、字典和管理数据分别提供下一步，不再跨业务误导。

## 6. 验证记录

静态与结构检查：

- JavaScript 语法与 Git whitespace 检查通过。
- 六个 HTML 的本地链接、重复 ID、页面标识、区域状态锚点和正式交互锚点检查通过。
- 需求编号统计确认第一期必须需求 55 项，编号与验收引用无悬空。
- 扫描旧冲突词、emoji 正式图标、低于 44px 的交互样式和假管理 `data-toast` 残留；未发现阻塞项。

浏览器实测（本地 HTTP，`360×800`）：

- 报表从“支出 → 分类”后标题为“分类消费占比”，图形标签为餐饮/日用/交通/其他。
- 点击餐饮下钻得到 `scope=expense&dimension=category&value=餐饮`，并携带 range、filters；返回恢复支出范围、分类维度和标题。
- 填报提交期间“保存支出”和“保存并继续”同时禁用。
- 个人字典新增后列表由 2 条变为 3 条；管理默认项停用后状态变为“已停用”；重置密码展示一次性结果。
- 报表区域 error 保留旧图表及主导航；登录 `state=empty` 不出现记账业务假空态。
- 登录夜晚模式应用为 `#11131A` 对应背景；报表和管理端均无横向溢出，当前可见正式控件没有小于 44×44px 的命中目标。
- 六页控制台无 JavaScript error。

## 7. 剩余边界

- 原型用于确认交互和需求，不替代真实后端的并发调整、租户隔离、审计不可抵赖、回收站到期事务和跨设备主题持久化测试。
- 非阻塞运营参数仍需在对应模块实现前校准，但不改变当前实体结构、必填性、认证主流程或报表时间边界。
- 精准坐标、地图、账户余额和自有账户转账属于后期增强，需单独立项与隐私评估。
