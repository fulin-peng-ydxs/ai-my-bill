# 个人账单 PWA 需求闭环

## 1. 初步需求理解

本产品是面向中国大陆个人和少量用户的手机优先记账应用。第一期采用 PWA 形态，仅通过受控内网访问并可添加到手机桌面，不以上架应用商店为目标。

产品聚焦三条主链路：快速填报商品级支出、快速填报金额型收入，以及从多维收支报表下钻到原始账目或调整记录。系统采用多租户设计，第一期一个普通用户对应一个独立租户；每位用户的数据完全隔离。商品名称在当前租户的商品字典内唯一，但同一商品可以形成多条历史支出记录。

当前项目已有需求闭环、正式需求、DESIGN、六页静态交互原型；T1-T28 已落地工程、安全、业务、页面、性能/容量/可观测性、安全权限专项和部署前发布候选门禁。T28 使用受 test profile、显式写开关和实时数据库指纹保护的一次性 PostgreSQL fixture，以及隔离 Chromium 复核普通用户/管理员关键链路，并锁定源码、JAR 和前端产物摘要，详见 [pre-release-test-report.md](pre-release-test-report.md)。运行概况不读取账目，操作日志只读且展示脱敏摘要；注销成功后在线个人数据、导出文件与全部会话立即删除，匿名安全审计保留 180 天。R22 的本地页面状态、权限、响应式与无障碍证据已关闭；R23、R55、当前无设备的实机抽样、真实备份恢复、目标入口 CSP/TLS、容器 secret 隔离和正式 PWA 发布验收仍保留在 T29。

## 2. 业务目标

- 降低记账操作成本，让用户可以快速完成一笔常见消费记录。
- 用与支出同等便捷但字段更少的表单记录收入，且收入名称与付款方必须明确。
- 将数据记录到商品明细级，使报表能够分析金额、数量、价格和商品出现频次。
- 让商品、支出分类、单位、资金渠道、购买渠道、常用地点、收入分类和付款方随着使用沉淀，做到越用越方便。
- 所有汇总指标均可下钻到组成指标的原始账单，保证统计结果可解释、可纠错。
- 严格隔离不同用户的数据，在低成本起步的同时保留稳定扩容和国内部署能力。

## 3. 用户角色、权限与使用场景

### 3.1 系统管理员

系统管理员负责：

- 以全局唯一用户名创建、启用和停用普通用户，并按需重置密码。
- 查看用户数量、账号状态、最近活跃情况和系统运行概况。
- 维护面向新用户的默认支出分类、收入分类、单位、资金渠道和购买渠道。
- 查看管理员操作记录，处理账号注销和数据导出相关问题。

系统管理员默认不能查看普通用户的收支明细。后续若出现客服协查需求，应增加用户主动授权、限时访问和完整操作留痕，不在第一期默认开放。

### 3.2 普通用户

普通用户可以：

- 新增、查询、修改、删除和恢复自己的支出与收入，记录或撤销退款/报销调整。
- 管理自己的商品、支出分类、单位、资金渠道、购买渠道、常用地点、收入分类和付款方。
- 查看自己的报表，并从报表下钻到原始账单。
- 导出或申请删除自己的数据。
- 管理个人默认设置和账号安全。

普通用户不能查看其他用户的数据，也不能访问系统管理能力。

### 3.3 典型使用场景

- 用户购物后立即打开手机桌面上的应用，选择最近使用商品，补充价格和数量后保存。
- 用户把明细中的常见支出或收入加入“日常”，下次直接选择模板回填，再确认本次金额与时间后保存。
- 用户在一次购物中购买多个商品，通过“保存并继续”连续录入多条商品明细。
- 用户收到工资、兼职费用或礼金时，填写收入名称、付款方、收入分类、金额、收款方式和时间后保存。
- 用户收到消费退款或费用报销时，从原支出记录调整，净支出随之降低，但不把款项重复算作收入。
- 用户可选择“家附近超市”等常用地点文本标签，未设置时保持“未指定”；第一期不采集坐标。
- 用户月底先看总收入、净支出和结余，再查看支出或收入专属维度并下钻核对。
- 用户发现价格或数量填错，从报表或明细页进入账单修改，报表随之重新计算。

## 4. 完整业务闭环

### 4.1 支出主链路

1. 用户登录后默认进入“记一笔”。
2. 用户搜索或选择商品；若是已有商品，系统带出其分类、常用单位、最近单价、最近支付方式和最近购买渠道。
3. 用户确认消费时间、商品、单位、单价、数量、支付方式、购买渠道（可选）和购买地点文本标签（可选）。
4. 系统实时计算应付金额；用户可填写实际支付金额，以承接优惠、抹零等场景。
5. 用户保存账单。系统防止重复提交，并给出明确的成功或失败反馈。
6. 保存成功后，系统更新当前用户的商品字典、最近使用记录和统计结果。
7. 用户可继续记下一笔、撤销刚才的保存，或进入刚保存的账单详情。
8. 用户在报表页按时间、分类、商品、支付方式、购买渠道、位置等维度分析数据，并下钻到具体账单。
9. 用户修改、删除或恢复账单后，所有相关报表按最新有效数据重新计算。

### 4.1.1 日常收支快捷闭环

1. 用户在有效收支列表项上左滑或长按，打开统一上下文操作后将该账目加入或更新为日常支出/收入；不在列表或编辑抽屉常驻收藏按钮。退款/报销调整和回收站账目不能作为来源。
2. 系统先执行与原账目类型一致的字段校验，再保存当前用户的日常模板。支出以规范化商品名称作为用户可理解的唯一业务键，收入以规范化收入名称作为对应业务键；内部仍使用稳定模板 ID，不能把可变展示名称直接当数据库主键。
3. 同类型、同业务键再次加入时更新既有模板，不产生重复项。支出商品改名或合并时模板随稳定商品引用迁移；收入同名但付款方或金额不同时，后加入的有效记录覆盖该名称模板。
4. 用户在“记一笔”页按当前类型进入“日常支出”或“日常收入”，选择模板后回填可复用业务字段，业务时间更新为当前上海时间，备注不复制，且不会自动提交。
5. 回填后仍执行普通新增账目的全部字段、字典启用状态、金额精度和权限校验。引用项已停用或失效时安全回退并明确提示用户确认，不静默提交旧值。
6. 用户可以从日常列表移除模板；移除不影响来源账目、商品字典或历史报表。来源账目后续删除不自动删除模板，但模板自身引用失效时按上一步处理。
7. 模板按最近使用排序并仅对当前租户可见。加载失败保留当前表单并可重试；空列表引导用户到有效明细中加入。
8. 日常模板只用于手动选择和预填，不创建周期任务、不自动记账，与后续建议的周期性收支能力保持边界。

### 4.2 收入与支出调整主链路

1. 用户在“记一笔”顶部切换到收入；系统恢复该用户上次类型偏好并保留支出、收入两份独立草稿。
2. 用户填写收入时间、收入名称、付款方、收入分类、金额和收款方式；这些字段全部必填，备注选填。
3. 新付款方可在当前表单快捷新增到个人字典；收入名称不要求唯一，可重复记录固定来源。
4. 保存请求防重复，失败保留输入；成功后收入进入明细和收入报表，保存并继续按收入规则保留默认项。
5. 消费退款或费用报销只能从一条有效支出的左滑或长按上下文操作发起，系统自动锁定并关联原支出。支持部分和多次调整，但有效累计金额不能超过原实付。
6. 调整不计入收入；报表展示原始支出、退款/报销冲减、净支出，总结余等于总收入减净支出。
7. 找不到原支出的款项不作为退款/报销调整录入；若业务实质为普通收入，则按收入主链路记录。
8. 自有资金渠道间转账不属于收入或支出；第一期不维护账户余额，也不记录内部转账。
9. 不提供独立调整入口；原支出移入回收站后关联调整冻结并退出报表，恢复后重新生效；存在关联调整时不能单独永久删除原支出。

### 4.3 支出字段与口径

每条账单代表一个商品明细，至少包含：

- 消费时间：必填，默认当前时间，允许修改；服务端以收到请求时的当前时间为权威，最多容忍客户端向未来偏移 5 分钟，超过即拒绝，并统一按 `Asia/Shanghai` 生成业务日期。
- 商品名称：必填，关联当前租户的商品字典。
- 一级分类：必填；二级分类选填，分类结构最多两级，选择已有商品时自动带出。
- 单位：必填，如个、件、斤、千克、次。
- 单价：必填，不得小于零。
- 数量：必填，默认 1，允许小数且必须大于零。
- 计算金额：由单价乘数量得到，供校验和展示。
- 实付金额：必填，默认等于计算金额，允许修改。
- 支付方式：必填，如微信、支付宝、现金、银行卡。
- 购买渠道：选填，默认“未指定”；可自定义并沉淀为字典，“未指定”使用空值而不是字典项。
- 购买位置：选填，第一期只支持“未指定”或常用地点文本标签；不请求定位权限、不保存坐标。
- 备注：选填。

金额报表统一以实付金额为口径，第一期使用人民币并按 `Asia/Shanghai` 解释业务时间、划分业务日期和聚合周期，已删除账单不参与统计。第一期每条账单都是一条商品明细，因此报表只能将其计为“消费明细数”，不能直接称为真实购物“笔数”或交易次数；如后续需要交易次数，应增加一次购物下多条商品明细的消费批次能力。

收入使用金额型表单，不包含商品、单位、单价、数量、购买渠道或地点：收入时间、收入名称、付款方、收入分类、金额和收款方式必填，备注选填。金额大于零、最多两位小数；收入名称去首尾空格后非空但不唯一；付款方去首尾空格后非空并形成个人字典；收款方式与支出的支付方式复用资金渠道字典。

### 4.4 商品唯一规则

- 商品名称仅在当前租户的商品字典内唯一，不要求跨租户唯一。
- 同一个商品可以被购买任意多次，每次形成独立消费记录。
- 判重前执行 Unicode NFKC、去首尾空格、内部连续空白折叠为一个空格并将英文转小写；展示名保留原样，不去标点、不自动合并同义词。
- 新增重名商品时，系统引导用户选择已有商品，不静默创建重复项。
- 商品支持改名、停用和合并；合并后历史账单统一归入保留商品且仍可追溯。
- 被历史账单引用的商品、单位、分类、支付方式、购买渠道和常用地点不能直接物理删除，应停用或合并。

### 4.5 状态流转

- 支出/收入：新建草稿 → 已保存 → 已修改或已删除 → 已恢复或永久清理。
- 日常模板：从有效账目加入 → 可选择回填 → 同业务键更新或手动移除；引用失效时进入需确认回退，不自动生成账目。
- 支出调整：从有效支出上下文创建并直接生效；随后可随原支出冻结、恢复生效、撤销或删除，不存在待归类状态。
- 字典项：启用 → 停用 → 重新启用；商品另支持合并。
- 普通用户：待启用 → 正常 → 已停用 → 恢复或注销。

第一期账单删除采用软删除并进入回收站 30 天，立即退出报表；期间可恢复，也可二次确认后永久删除。到期由可审计后台任务清理，清理后不可恢复，备份副本按备份生命周期自然过期。

原支出移入回收站时，关联调整同步冻结并退出报表；恢复原支出时重新生效。存在关联调整的原支出不得单独永久删除，必须先处理调整，或二次确认后在同一事务内连同调整清理，避免孤立调整。

### 4.6 失败处理与回退

- 网络异常或保存失败时保留本地填写内容，不清空表单，并允许重试。
- 保存请求携带防重复标识，避免重复点击或网络重试产生重复账单。
- 会话失效时提示重新登录；登录成功后恢复尚未提交的本地草稿。
- 删除成功后提供即时撤销入口，同时可在回收站恢复。
- 报表加载失败时保留筛选条件并允许重试。
- 字典项冲突时说明冲突对象，并提供选择已有项或合并入口。
- 修改账单失败时保留用户编辑内容，不以旧数据覆盖未提交内容。
- 收支类型切换不清空另一类型草稿；付款方快捷新增失败时保留收入表单。
- 日常模板加载或回填失败不覆盖当前草稿；失效字段只回退对应字段并要求再次确认。
- 并发退款/报销导致累计超额时拒绝后到请求，刷新原支出及已生效调整后允许重试。

### 4.7 闭环成立标准

- 普通用户能独立完成从登录、记录支出或收入、记录支出调整、查看报表、下钻明细到纠错的全过程。
- 保存、修改、删除和恢复账单后，对应报表结果保持一致。
- 用户重复购买相同商品时不会产生重复商品字典项。
- 任一普通用户均不能读取、修改或推断其他租户的数据。
- 网络失败、误删除和重复提交均有明确且可恢复的处理路径。
- 收入、支出和调整不存在重复统计；收入名称、付款方必填且能在明细、报表和导出中追溯。
- 任一有效收支可加入日常，同名模板不重复；模板回填不自动保存，且仍通过普通填报的全部治理规则。

## 5. 完整功能点清单

### 5.1 账号与租户

- **功能目标**：识别当前用户并隔离全部业务数据。
- **入口**：登录页、我的、系统管理后台。
- **关键操作**：用户名密码登录、首次设置正式密码、退出、联系管理员重置密码、用户启停和注销。
- **系统反馈**：明确显示成功、失败、账号停用或会话失效状态。
- **状态变化**：用户账号在待启用、正常、停用和注销间流转。
- **权限要求**：普通用户只访问自己的租户数据；管理员只管理账号和系统配置。
- **异常处理**：异常登录、越权请求和失效会话均被拒绝并留下必要的安全记录。

### 5.2 快速收支填报

- **功能目标**：在同一入口以尽量少的操作完成商品级支出或金额型收入记录。
- **入口**：登录后的默认页及底部“记一笔”。
- **关键操作**：切换支出/收入、选择日常模板、填写各自字段、保存、保存并继续、撤销。
- **系统反馈**：实时计算金额，显示日常模板回填、字段校验、保存进度和保存结果。
- **状态变化**：日常模板可从有效账目加入、同键更新或移除；选择模板只更新当前草稿，确认保存后才创建账单并更新个人字典的最近使用信息。
- **权限要求**：只能操作当前用户自己的字典和账单。
- **异常处理**：本地保留草稿、防重复保存、失败后原位重试；日常模板引用失效时只回退对应字段，不清空其他已回填内容。

### 5.3 商品及字段字典

- **功能目标**：沉淀可复用选项，使填报越用越快。
- **入口**：填报下拉中的快捷新增，以及“我的”中的字典管理。
- **关键操作**：新增、改名、排序、停用、恢复和商品合并。
- **系统反馈**：重复检测、引用提示、合并影响提示和操作结果。
- **状态变化**：字典项启停，商品合并后更新统计归属。
- **权限要求**：系统默认项由管理员维护；用户可以维护个人项，且个人操作不影响其他租户。
- **异常处理**：有历史引用时禁止物理删除；重名时引导复用或合并。

商品字典应保存商品名称、分类、默认单位、最近单价、最近支付方式、最近购买渠道、使用频次、最近使用时间和启用状态。

收入分类和付款方均为个人字典，支持新增、改名、排序、停用、恢复和历史引用保护。收入名称不是唯一字典，只保留最近使用以加速输入。支付方式与收款方式复用同一资金渠道数据，在不同表单使用对应场景文案。

### 5.4 收支明细、调整与纠错

- **功能目标**：统一查询和纠正支出、收入与退款/报销调整，同时保留类型专属字段。
- **入口**：底部“明细”及各报表下钻入口。
- **关键操作**：默认查看今天、常驻全局搜索、按类型/资金渠道/预设或指定日期组合筛选；按日期分组、每批最多加载 20 笔；短按查看编辑，左滑或长按后删除、加入日常或从具体支出记录调整。
- **系统反馈**：展示筛选条件、分批加载进度、结果数量、修改结果及报表刷新状态。
- **状态变化**：账单修改、软删除、恢复或永久清理。
- **权限要求**：只能访问当前租户账单。
- **异常处理**：修改冲突时提示刷新并保留当前输入；导出失败可以重试。

### 5.5 多维收支报表

- **功能目标**：先理解收入、净支出与结余，再逐步定位收支结构、价格变化和异常记录。
- **入口**：底部“报表”。
- **关键操作**：使用页面常驻全局搜索，选择预设或指定日期、账目范围与类型专属条件，切换维度并点击图表下钻。
- **系统反馈**：显示统计口径、筛选条件、加载状态、空状态和错误状态。
- **状态变化**：报表本身不改变业务数据；下钻会将筛选上下文带入明细页。
- **权限要求**：只统计当前租户的有效账单。
- **异常处理**：加载失败保留条件；无数据时引导用户记第一笔账。

报表维度至少包括：

| 范围/维度 | 指标和分析口径 |
| --- | --- |
| 收支总览 | 总收入、原始支出、退款/报销冲减、净支出、结余和趋势 |
| 时间 | 日、周、月、季度、年消费，累计趋势、环比和同比 |
| 分类 | 一级和二级分类金额、占比、趋势和排行 |
| 商品 | 总消费、消费明细数、总数量、平均单价、最近价格和价格趋势 |
| 支付方式 | 金额、消费明细数、占比和趋势 |
| 购买渠道 | 金额、消费明细数、占比和趋势 |
| 位置 | 按常用地点聚合的金额、消费明细数、占比和趋势 |
| 消费习惯 | 星期分布、时段分布、日均、月均和单笔均值 |
| 价格 | 最低价、最高价、平均价、最近价和异常价格 |
| 频次 | 高频商品、最近购买、复购间隔和长期未购买商品 |
| 数据质量 | 未分类、疑似重复和异常高价记录 |
| 收入分类 | 金额、收入明细数、占比、趋势和排行 |
| 付款方 | 金额、收入明细数、占比、趋势和排行 |
| 收入名称 | 金额、出现频次、最近记录和趋势 |
| 收款方式 | 金额、收入明细数、占比和趋势 |

不同单位的数量不能直接相加。同一商品存在多个单位时，按单位分别统计数量和单价，金额仍可汇总。价格报表默认展示用户填写的单位价格；如需体现优惠后的实际单位成本，可另以“实付金额 ÷ 数量”展示，并与填写单价明确区分。

T22 已将数据质量规则固化为 `expense-quality-v1`：异常高价只在同商品、同单位、过去 180 天至少有 3 条有效历史样本时，以实际单位成本与历史中位数比较，超过 50% 才提示；疑似重复按同商品、实付金额和资金渠道在 10 分钟内再次出现提示。软删除、冻结或失效账目排除，规则只提示并下钻到原账目，不修改、标记、合并或删除。一级分类由数据库约束必填，因此当前模型不会产生未分类支出，质量页不伪造该类线索。

T23 已在 T21 收入时间趋势基础上补齐收入分类、收款方式、付款方、收入名称和频次排行；金额维度展示金额、明细数和占比，名称/频次同时展示最近记录，频次额外展示累计收入。停用的分类、付款方和资金渠道按历史快照继续可追溯，所有维度只统计当前租户的有效正常收入并可精确下钻。

T24 已完成系统管理四模块：用户与默认字典沿用既有真实操作，运行概况只读取账号状态、最近活跃、有效会话、服务连通和数据库占用，操作日志按管理员、动作、对象、结果和时间只读筛选并查看脱敏详情。普通用户即使直接访问管理路由也不会加载管理数据；真实备份能力未提前实现，在 T29 接入前明确显示未配置。

T25 已完成六页本地页面验收：七个 DESIGN 关键视口均无整页横向溢出，手机/平板可见操作达到 44px，键盘焦点、抽屉关闭与焦点恢复、背景锁滚动、低高度、双主题及 permission 均可观察。首次会话等待不会猜测角色或挂载受限页面；集合空态、主动失败、静默刷新失败保留旧值和恢复入口按真实语义区分。当前无连接 iOS/Android 设备，实机抽样明确未执行并留待 T29。

T26 已完成可复现的本地性能、容量与可观测性基线：代表性数据确认明细分页与清理索引、报表服务端聚合、导出游标和清理固定批次边界成立；指标只暴露有限基数运行信号并受管理员权限保护。生产主机资源曲线、Prometheus/通知渠道接入、真实告警和备份新鲜度仍属于 T29 环境证据，未以本地数据冒充完成。

### 5.6 个人设置与数据权利

- **功能目标**：管理个人默认值、账号和个人数据。
- **入口**：底部“我的”。
- **关键操作**：设置默认资金渠道；在“数据与安全”中管理八类个人字典、导出数据和修改密码；在独立“账号操作”分组中退出或注销。
- **系统反馈**：展示设置生效结果、导出进度和注销影响；退出登录与注销账号居中展示，前者以主交互色标识普通会话动作，后者以危险色标识不可逆流程。
- **状态变化**：个人偏好更新；注销进入受控处理流程。
- **权限要求**：只处理当前用户配置和数据。
- **异常处理**：导出失败可重试；注销必须二次确认。

### 5.7 系统管理

- **功能目标**：以最小运营能力维护少量用户和系统默认值。
- **入口**：与普通用户入口隔离的管理后台。
- **关键操作**：用户创建、密码重置、启停、默认字典维护、运行概况查看和操作日志查询。
- **系统反馈**：显示操作影响、执行状态和失败原因。
- **状态变化**：用户账号状态和系统默认配置变化。
- **权限要求**：仅系统管理员可访问；敏感管理操作必须留痕。
- **异常处理**：禁止管理员误改普通用户个人字典和收支数据。

## 6. 页面闭环草案

### 6.1 登录与安装引导

- **页面职责**：完成登录、密码找回和 PWA 添加到桌面的分平台引导。
- **衔接关系**：登录成功后默认进入“记一笔”；会话过期后回到登录页并保留本地草稿。
- **权限边界**：未登录用户不能访问账单、报表和管理能力。
- **异常反馈**：区分凭据错误、账号停用、网络异常和系统异常。

### 6.2 记一笔

- **页面职责**：承载商品级支出和金额型收入快速填报，是普通用户登录后的默认首页。
- **关键链路**：选择类型 → 填写该类型字段 → 确认金额 → 保存；两类草稿互不覆盖。
- **衔接关系**：保存后可以继续录入、查看刚保存记录或撤销；新增字典项后返回当前表单并自动选中。
- **数据变化**：新增支出或收入，更新对应字典、最近使用信息和报表数据。
- **权限边界**：只展示当前用户的商品和字典项。
- **异常反馈**：字段错误就地提示；保存失败不清空；重复提交不生成重复数据。

### 6.3 报表

- **页面职责**：展示当前时间范围的收支总览、分类型趋势、结构和异常线索。
- **关键链路**：全局搜索或选择全部/支出/收入与高级筛选条件 → 查看图表 → 点击指标或维度项 → 下钻明细。
- **衔接关系**：下钻时把统计口径和筛选条件传给明细页；从明细纠错返回后重新计算。
- **数据变化**：只读取和聚合账单，不直接修改账单。
- **权限边界**：仅统计当前租户有效数据。
- **异常反馈**：空状态给出记账入口；加载失败保留筛选条件和重试入口。

### 6.4 明细

- **页面职责**：承接支出、收入和调整查询以及所有报表的原始数据追溯。
- **关键链路**：默认今天 → 全局搜索或组合筛选 → 按日期分组并分批加载 → 短按查看详情，或左滑/长按后删除、加入日常、从具体支出记录调整 → 返回原筛选结果。
- **衔接关系**：从报表进入时继承条件；修改后通知报表刷新。
- **数据变化**：修改、软删除、恢复或永久清理账单。
- **权限边界**：只访问当前租户数据。
- **异常反馈**：无结果区分“没有账单”和“筛选后无匹配”；冲突或失败时保留编辑内容。

### 6.5 我的

- **页面职责**：承接字典、默认偏好、数据导出、账号安全和 PWA 安装帮助。
- **衔接关系**：字典修改后返回填报页立即生效；停用项不再出现在新填报默认下拉中。
- **数据变化**：更新个人设置、字典和账号状态。
- **权限边界**：只管理当前用户的数据与设置。
- **异常反馈**：删除、合并、导出和注销等高影响操作明确说明后果并二次确认。

### 6.6 系统管理后台

- **页面职责**：管理用户、默认字典、系统概况和管理员操作日志。
- **入口关系**：与普通用户手机端导航隔离，主要适配桌面端，同时保持手机可访问。
- **数据变化**：改变账号状态和新用户默认配置，不直接改变现有用户的个人配置。
- **权限边界**：仅管理员可见；普通用户即使直接访问地址也会被服务端拒绝。
- **异常反馈**：对启停、注销等操作显示影响范围和处理结果。

普通用户手机端底部导航固定为：`记一笔｜报表｜明细｜我的`。

## 7. 已确认结论与关键决策

以下结论已经由用户明确确认，可直接进入后续需求与设计：

- 第一阶段一个普通用户对应一个独立租户，不支持家庭共享账本。
- 商品名称在当前租户的商品字典内唯一，同一商品可以产生多条历史消费记录。
- 第一阶段采用 PWA，不要求从应用商店下载安装。
- 主要服务中国大陆个人和少量用户。
- 账号使用用户名和密码，由管理员创建；16 位临时密码仅展示一次、24 小时有效，首次登录设置正式密码，管理员重置后旧会话失效。
- 商品按 NFKC、首尾清理、内部空白折叠和英文小写生成租户内唯一键，展示名保留原样。
- 单价最多 4 位小数、数量最多 3 位小数、金额 2 位小数，十进制精确计算并使用 `ROUND_HALF_UP`；上限按正式需求 §3。
- 回收站保留 30 天，支持恢复和二次确认永久删除，到期由后台清理。
- 第一期地点仅为可选文本标签；精准定位和地图选点移入后期增强。
- 收入采用金额型表单；收入时间、收入名称、付款方、收入分类、金额和收款方式必填，收入名称不唯一，付款方形成个人字典。
- 退款和报销关联并冲减原支出，不计入收入；支持部分和多次调整但累计不超过原实付。
- 第一期不做账户余额和自有账户转账，转账不计收支。
- 收入使用红色体系、支出使用绿色体系并辅以类型文字和正负号；图表和非文字强调分别固定使用 `#FF3B30`、`#34C759`，金额、标签和状态文字消费 DESIGN 定义的明暗主题可读前景色，红绿不承担普通操作或装饰。
- 支出分类最多两级，一级必填、二级选填；购买渠道选填并默认“未指定”；第一期固定人民币和 `Asia/Shanghai`。
- 调整只能从有效支出上下文创建并自动关联；原支出删除时关联调整冻结，恢复后重生效，永久删除不得留下孤立调整。

原 B1-B9 与收入板块关键决策已全部关闭并同步到正式需求、DESIGN 和原型，完整收支范围可进入统一开发计划。

## 10. 推断依据与推断决策

### 10.1 产品形态

用户明确要求手机应用和低成本部署，因此第一期采用单代码库 PWA。PWA 通过浏览器访问，可添加到手机桌面，并可在后续需要时再评估应用商店封装，不在第一期承担原生双端开发和审核成本。

### 10.2 已确认的低成本部署方向

用户已确认第一期采用 Vue 3 前端、Java/Spring Boot 模块化单体、PostgreSQL/Flyway 和 Docker Compose 单机同源部署：

- 单台 Linux 主机运行反向代理、前端静态资源、Spring Boot 和 PostgreSQL；按用户确认使用服务器内网 IP 直接访问（`https://<内网IP>:<独立端口>`），不购买或绑定自有域名；保留全站 HTTPS。
- 同源 Cookie 会话降低跨域认证复杂度，但团队同时承担主机补丁、数据库、备份恢复和容量告警责任。
- 第一阶段不上传票据图片，不引入 Redis、消息队列或微服务，以控制存储、带宽与运维成本。
- 多租户隔离必须同时落实到应用查询、复合归属约束和 PostgreSQL RLS；应用运行角色不得拥有表、超级用户或 `BYPASSRLS` 权限。

IP 入口须使用客户端明确受信任的内部 CA 签发证书，证书 SAN 包含实际内网 IP；受控电脑与手机安装并信任 CA 后验证 HTTPS 和 PWA。保留证书续期、加载和到期告警要求，CA 私钥与应用隔离。不能用明文 HTTP、关闭证书验证或点击忽略警告代替验收。

一期仅内网，不配置公网端口映射或公网入口，公网 IP、域名及公网备案不作为本阶段前置。内网部署仍需验证允许网段、非授权网络拒绝、同源 Cookie/CSRF、租户/RLS 隔离、最小权限、日志脱敏、补丁维护、备份恢复和告警。RPO/RTO 与终端信任等未确认事项仍是发布门禁；后续开放公网时重新评估公网接入及备案。

### 10.3 便捷性策略

第一期不依赖 AI 也能显著降低操作成本，优先采用：

- 最近使用和高频选项优先排序。
- 选择商品后自动带出分类、单位、最近价格、支付方式和最近购买渠道。
- 默认数量为 1、默认时间为当前时间。
- 支持从有效明细加入日常模板、选择模板回填和保存并继续。
- 本地保留未提交草稿。

OCR、自然语言记账等能力需要额外的识别、纠错和成本控制闭环，留到基础数据质量稳定之后评估。

## 11. 后续建议

正式需求、六页 HTML 原型、验收矩阵和 DESIGN 契约均已建立。进入开发计划前应以 [requirement.md](requirement.md) 为业务事实源，并以以下门禁复核：

- 56 项一期需求的编号、来源、页面承载和验收矩阵保持一一追溯。
- 页面级与区域级 loading、empty、error、permission 状态按所属阶段逐步关闭。
- PostgreSQL RLS、角色隔离、备份恢复、完整导出字段和中国大陆部署条件进入对应开发里程碑。
- 手机与桌面响应式、触控尺寸、明暗主题以及关键业务交互通过自动化和浏览器回归。
